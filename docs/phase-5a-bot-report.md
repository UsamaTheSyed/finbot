# FinBot Phase 5A — implementation and verification report

Baseline: **e1c9d83**. Prepared 2026-10-08. This is an implementation handoff with outstanding environment-dependent verification, **not an unconditional Phase 5A completion certificate**.

1. **Pre-flight architecture audit.** Existing React/Vite/TypeScript frontend, CSS architecture, React Router, TanStack Query and Zustand retained. Backend is Fastify 5 with cookie sessions, salted password hashing, Drizzle 0.44 and PostgreSQL via pg. Active workspace membership is the existing authorization boundary. Payment service was reusable; invoice creation, party summaries and reports were embedded in routes and were extracted without replacing their accounting behavior. No existing bot/AI implementation or provider SDK was present. No new dependency was installed or added. Existing broad active-member financial permissions are preserved; this phase does not redesign team permissions.

2. **Bot architecture.** Telegram adapter → normalized message → durable conversation engine → schema-validated language extraction → fixed read/prepare tools → confirmation → shared financial services. AI never gets a database connection, session, SQL executor or arbitrary tool executor. Normalized core types contain no Telegram API objects.

3. **Modules.** `server/bot/{ai,channels,core,security,tools}`, `server/bot/types.ts`, config, polling entry point and metadata maintenance command. `server/routes/bot.ts` exposes authenticated linking/status/disconnect and optional webhook delivery. Frontend additions are one existing-card integration component and a service.

4. **Database tables.** `bot_identities` binds channel/user/chat to the existing user/workspace; `bot_link_tokens` stores SHA-256 token hashes and expiry/use timestamps; `bot_conversations` stores structured context; `bot_actions` stores validated proposals/status/result; `bot_receipts` deduplicates messages without retaining text; `bot_audit` records action metadata; `bot_rate_limits` stores durable counters; `bot_runtime` stores the polling offset. Foreign keys and a unique external identity index protect associations. No duplicate User or ledger model.

5. **Migration.** Additive `0002_bot_core.sql`, matching Drizzle snapshot and journal entry. Existing migrations 0000/0001 are unchanged. Financial tables/data are not reset by this migration. Migration execution against PostgreSQL remains a local verification gate.

6. **Telegram architecture.** Native fetch against the official Bot API; text, inline keyboards, callback acknowledgements and outgoing plain text. Only private human chats with matching user/chat identity are accepted; groups, bot senders and unsupported media are ignored. Long polling persists its offset and takes a database advisory lock to prevent two pollers. Existing webhooks are detected and not silently deleted. Webhook mode validates the Telegram secret header with a constant-time comparison. No production deployment or webhook registration was attempted.

7. **Account linking.** Authenticated Settings action generates 32 random bytes encoded as a five-minute one-use token. Only its hash is stored. A deep link invokes `/start TOKEN`; `/link TOKEN` is also supported. Consumption locks the token, verifies expiry/use and current membership, then creates the identity and marks the token used atomically. Reissuing invalidates older links for that user/workspace. Token responses are `no-store`; no session cookie is sent through Telegram. Disconnect revokes the association and dependent pending state, not financial records.

8. **Workspace security.** Every linked request resolves its persisted identity and active membership. Membership is rechecked during confirmation. Read candidates are scoped SQL queries; selected entities are revalidated. Pending actions are loaded by action ID plus channel identity, user and business, under a row lock. Natural language and callback text cannot supply trusted workspace/entity IDs. Web linking changes require a custom same-origin header and reject cross-site origins. The server supports one workspace per Telegram account at a time.

9. **AI provider/model.** One provider: OpenAI Chat Completions using configurable `gpt-4.1-mini-2025-04-14`. Native fetch keeps SDK dependencies out of the project. Structured JSON schema, `store:false`, a 20-second request timeout and a 1,000-output-token cap are set. No live model call was made without credentials. Provider retention is governed by the user's provider account; `store:false` is not a promise of zero provider-side retention.

10. **Structured schema.** A strict Zod extraction object allows only bounded intent, confidence and explicit nullable language fields. It has no SQL, internal party ID, internal invoice ID or workspace ID field. Executable pending payloads use a second discriminated schema composed from the existing payment/invoice validators. Provider refusal, truncated/malformed output, extra fields or failure cannot execute a write.

11. **Intents.** GREETING, HELP, SEARCH_PARTY, GET_PARTY_BALANCE, GET_PARTY_STATEMENT, SEARCH_INVOICE, GET_INVOICE, GET_OUTSTANDING_INVOICES, RECORD_PAYMENT, RECORD_SALE, RECORD_PURCHASE, GET_DAILY_SUMMARY, GET_RECEIVABLES, GET_PAYABLES, GET_CASH_FLOW, CANCEL, CONFIRM, EDIT_PENDING_ACTION and UNKNOWN. RECORD_PURCHASE returns an explicit unsupported response because the baseline lacks a purchase-create service. Model-generated CONFIRM is never execution authority.

12. **Tool definitions.** Fixed code dispatches known intents. `searchParty`, `searchInvoice`, `readTool`, `prepareWrite`, `executeWrite` adapt established services. No dynamically named or model-created tool is executed. Purchase prepare/execute is unavailable rather than a separate simplified purchase ledger.

13. **Read tools.** Party search/balance/recent statement entries, invoice search/detail/outstanding, daily/week-to-date/month-to-date summaries, dashboard receivables/payables and monthly cash flow. Results are formatted directly from backend values; the model does not paraphrase or approximate financial numbers. Party statement shows up to 20 recent entries plus authoritative current balance; it directs the user to FinBot for the full statement. Cash-flow reports accept a reporting month. A/R and A/P answers explicitly use the existing dashboard definitions.

14. **Mutation tools.** Payment preparation calls `validatePayment`; confirmed execution calls `executePayment`. Sale preparation calls existing invoice validation/calculation; execution calls `insertInvoiceGraph` and `allocateInvoiceNumber`. Sale conversations currently collect a single item, with explicit quantity, unit, rate, tax, discount, paid amount, method and dates. Multi-item creation remains available in the web app. No automatic party creation or purchase accounting was added.

15. **Confirmation architecture.** Preparing a proposal performs validation only, then saves bot metadata. The summary displays resolved party, exact PKR amount, method, absolute date and allocation; sales also show item/tax/discount/paid/due date. Confirm/Edit/Cancel buttons contain an opaque action UUID. Exact textual confirm/edit/cancel can operate on the current pending proposal without AI. Edit cancels the old action and requires a new validated summary/confirmation.

16. **Pending actions.** Persisted states: pending, confirmed, executed, cancelled, expired, failed. Default TTL 15 minutes, configurable from 1–60. Expiry is checked in PostgreSQL at confirmation. Pending financial payloads are validated schemas, not arbitrary AI output. Stale/cancelled/foreign buttons cannot execute. Financial execution and final action status/result commit in the same transaction; failures roll back the financial savepoint before marking the action failed.

17. **Idempotency.** A channel/user/chat/update receipt and advisory transaction lock serialize duplicate messages across engine instances. Action row locking plus terminal status prevents repeat execution even for separate double-click updates. Polling offsets survive restarts. The financial commit and executed-action result are atomic. If sending the reply fails after a commit, a retry cannot duplicate the write; the user can confirm again to retrieve the already-executed result or inspect FinBot. Exactly-once Telegram message delivery itself is not claimed.

18. **Conversation state.** Structured extraction, resolved selections and opaque option keys persist in PostgreSQL for 30 minutes. Required-field replies and button choices avoid new AI calls. Only explicitly supplied edits are merged. New selections are always validated by scoped domain services. The LLM is not responsible for remembering balances or authorization.

19. **Normalization.** Deterministic integer-paisa parsing accepts 15000, 15,000, 15k, 15 K, 15 hazar, 15 thousand, 1 lakh and 1 lac, with bounded precision/range. Relative dates use each business timezone; ambiguous `kal` prompts for an absolute date. Mutations require a single date, not a range. A concrete shared validation bug was corrected: valid decimals such as 100.10 no longer fail due to floating-point multiplication; excessive precision remains rejected.

20. **Ambiguity.** Multiple parties produce opaque selection buttons; more than ten matches require a narrower name. Missing parties are not fabricated. Payment allocation is explicitly selected, including on-account where supported, unless an explicit reference resolves uniquely. Multiple matching references are not guessed. On-account payments do not pretend to settle invoices. Missing payment method is asked using existing domain options. Low confidence asks for clearer input, with no financial write.

21. **Audit.** Workspace, user, channel, update ID, interpreted intent, pending action ID, timestamp and result are stored. Confirmation results retain the created ledger ID or failure code, even if later unlinking removes action payloads. Technical diagnostics log only stage and sanitized code, never entire exception objects, conversation text, provider URLs, SQL parameters or credentials. Web disconnects are audited. Audit events are retained; no audit-retention policy was invented for this phase.

22. **Rate limiting.** Database counters: 30 messages/minute per external user; 5 link attempts/5 minutes; 5 link-generation requests/5 minutes per FinBot user; 12 AI calls/minute per identity; 200 AI calls/hour globally. AI failures still consume attempt budget. Existing deterministic help/confirmation/cancellation and structured continuation avoid AI calls.

23. **Privacy/security.** Input limit 2,000 characters, webhook body limit 32 KiB, bounded result lists and output length. AI receives only the user's current message and minimal date/intent context; no ledger histories or disambiguation records. Link tokens, Telegram/OpenAI keys, cookies and webhook secrets stay server-side. Telegram replies use plain text and protected-content mode. No HTML/Markdown supplied by the user is interpreted by the bot. `bot:prune` removes expired metadata and old action payloads; financial/audit records are retained. Protected-content mode cannot prevent a recipient taking a screenshot.

24. **Routes.** Added GET `/api/businesses/:businessId/bot/telegram`, POST `.../telegram/link`, DELETE `.../telegram`, and optional POST `/api/bot/telegram/webhook`. Existing invoice/party/report route signatures are unchanged and now delegate extracted functions. Existing payment routes retain their transaction-owning service wrapper.

25. **Reused services.** Active membership, scoped record lookup, invoice/payment DTOs, payment validation/execution, invoice graph creation, invoice numbering, invoice calculation, party summaries, dashboard report and financial report. No CSS-to-Tailwind migration, library replacement, router redesign or second accounting implementation.

26. **Tests added.** Twelve standalone bot tests cover amount/date/schema safety, representative language-output boundaries, malformed/provider failure, private-chat normalization, callback identity, fake transport config/hash defaults and real Fastify unauthenticated/webhook guards without live services. Thirteen PostgreSQL/API subtests are appended to the existing integration test so destructive seeds do not race across files: secure linking/API/webhook guard, real-data reads, partial/full payments, restart context, concurrent duplicate confirmation, cancellation/expiry/edit, party/invoice ambiguity, identity/workspace revocation, cross-workspace payload rejection, sale graph/numbering, AI failure/unsupported purchase and unlink/audit preservation. Three viewport cases test Settings linking/disconnect with a fake bot route. Deterministic AI fixtures verify the structured boundary; they do not prove live language-model quality.

27. **Executed test results.** `npm test`: **40 passed, 0 failed, 1 skipped** (41 top-level tests). Of the passing tests, 12 are new standalone bot tests and 28 are existing non-database tests. The PostgreSQL parent and its 13 new nested checks did not execute because TEST_DATABASE_URL/PostgreSQL are unavailable. Bot category: **12/12 passed** within the full suite. New integration helper and test entry point receive an additional TypeScript check.

28. **Browser result.** 48 cases discovered (45 existing + 3 new). Execution attempted but server startup was blocked by environment `EPERM` on the tsx IPC socket; PostgreSQL is also unavailable here. **No current browser pass count is claimed.** The user's baseline was 45 passing; this patch must be run locally to establish regression status.

29. **Frontend build.** Strict frontend typecheck and Vite production build passed. Existing lazy routes and CSS architecture are preserved.

30. **Backend build.** TypeScript backend production build passed. ESLint completed with zero warnings/errors. No new dependency or lockfile update is required.

31. **Live smoke test.** Not run: no Telegram bot/OpenAI credentials were supplied. Exact local steps are in `PHASE-5A-BOT-APPLY.md`, including no-write-before-confirm, persistence after restart, duplicate confirmation and web reconciliation. This is a remaining completion gate.

32. **Environment.** Added TELEGRAM_MODE (off by default), TELEGRAM_BOT_TOKEN, TELEGRAM_BOT_USERNAME, TELEGRAM_WEBHOOK_SECRET, OPENAI_API_KEY, OPENAI_MODEL and BOT_ACTION_TTL_MINUTES. Existing DATABASE_URL/TEST_DATABASE_URL/session settings remain unchanged. Only `.env.example` is included; local `.env` must not be overwritten.

33. **Changed files.** Exact paths and hashes are in `docs/phase-5a-file-manifest.json`. The delivery ZIP includes only changes against the supplied e1c9d83 archive. Major areas are bot modules/schema/routes, extracted shared services, the existing Telegram Settings card and tests. Existing `PHASE-5A-APPLY.md` from an older frontend phase is untouched; use the new `PHASE-5A-BOT-APPLY.md`.

34. **Known limitations.** Database, browser and live-service execution are not verified here; no completion certificate is warranted until those gates pass. Single-item conversational sales only. Purchase creation unavailable in existing backend. Full statements and longer result sets remain in web UI. No live push refresh from bot into an already-open browser. No automatic bot metadata scheduler. One linked workspace per Telegram account. Figma Settings frame `783:2446` / Telegram card `783:2587` in file `MhAa3QpnuICXqjLSsOe5B2` was inspected; existing card structure/tokens/assets are retained, but browser screenshot comparison of the new connection states is pending.

35. **Deferred.** WhatsApp, n8n, voice/transcription, OCR, PDF, email, bank/payment-provider APIs, billing, mobile, production deployment and a new purchase-create domain. Easypaisa/JazzCash remain ledger method labels only.

36. **Phase 5B recommendation.** First close the Phase 5A local gates and review live conversation quality/error recovery. Then separately agree the next channel or broader conversational workflow, role-specific bot permissions, operations/monitoring and retention policy. Do not begin WhatsApp or production deployment without explicit authorization.
